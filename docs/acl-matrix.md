# Access Control Matrix

**Security model for the Access Recertification scoped application**

**Application scope:** `x_2182277_access_0`

All ACLs are of type **record** with Decision Type **Allow If** and **Admin overrides** enabled.

---

## 1. How ACLs Evaluate in ServiceNow

Three properties drive every decision below:

1. **ACLs are permissive.** A rule grants access; it does not withhold it. Access is denied only when no matching rule passes.
2. **ACLs are cumulative.** If several rules match an operation, any one of them passing is sufficient. A broad unconditioned rule therefore defeats a narrow scripted rule sitting beside it.
3. **Admin overrides record ACLs.** A user holding `admin` bypasses these rules entirely. Testing row-level security against an account with a standing admin grant produces a false result—see the Verification section of the main README.

> **Design consequence:** Restricting access means editing or removing the broad rule, not adding a narrow one alongside it.

Evaluation order for a record operation is **table-level ACL → field-level ACL**, with business rules and UI policies running separately:

- UI policies run client-side on form render.
- Business rules run server-side around the database operation.
- A UI policy is presentation; an ACL is enforcement.
- Hiding a field in a UI policy does not secure it.

## 2. Access Item

**Table:** `x_2182277_access_0_access_item`

| Operation | Role | Condition | Intent |
|---|---|---|---|
| `create` | `.user` | None | Any requester may ask for access. Creation is not the control—manager approval is. |
| `create` | `.access_manager` | None | Managers may record entitlements directly, such as backfilling existing access. |
| `create` | `.admin` | None | Administrative. |
| `read` | `.user` | `answer = (current.user == gs.getUserID());` | A requester sees only their own entitlements. |
| `read` | `.reviewer` | None | Reviewers need entitlement detail—application, access level, and justification—to make a certification decision. |
| `read` | `.access_manager` | None | Oversight across all entitlements. |
| `read` | `.admin` | None | Administrative. |
| `write` | `.access_manager` | None | Managers may correct entitlement data. |
| `write` | `.admin` | None | Administrative. |
| `delete` | `.admin` | None | Deletion is restricted to administrators. Revocation is a status change, not a deletion—the record is the audit trail. |

### Create/Read Asymmetry

The `create` ACL is deliberately unconditioned while the `read` ACL is scripted. Anyone may submit a request; nobody sees anyone else's.

If creation were restricted, the Service Catalog item built for requesters would be unusable by requesters—which was the case before Phase 8 verification uncovered it.

## 3. Access Review

**Table:** `x_2182277_access_0_access_review`

| Operation | Role | Condition | Intent |
|---|---|---|---|
| `read` | `.reviewer` | `answer = (current.assigned_to == gs.getUserID());` | Reviewers see only reviews assigned to them. |
| `write` | `.reviewer` | `answer = (current.assigned_to == gs.getUserID());` | Reviewers act only on their own assigned work. |
| `read` | `.access_manager` | None | Oversight—campaign progress and completion reporting across all reviews. |
| `create` | `.admin` | None | Reviews are generated by the scheduled flow running as System, not created by hand. |
| `delete` | `.admin` | None | Completed reviews are certification evidence and must persist. |

### Separation of Duties

The access manager holds **read without write** on Access Review. This is the central control of the model:

- An access manager can see every review, report on campaign progress, and identify overdue work.
- An access manager cannot certify or revoke—that decision belongs solely to the assigned reviewer.

The person who monitors whether the review happened is not the person who decides its outcome. Without this split, oversight and decision-making collapse into one role, and the campaign becomes self-attesting.

## 4. Field-Level Control

**Field:** `x_2182277_access_0_access_review.revocation_reason`

| Operation | Role | Condition |
|---|---|---|
| `write` | `.reviewer` | `answer = (current.assigned_to == gs.getUserID());` |

A revocation reason is the justification attached to a control decision. Only the reviewer who made the decision may write it.

Field-level ACLs evaluate after the table-level ACL for the same operation. **Both must pass.**

A UI Policy makes this field mandatory and visible when `Decision = Revoke`, but that is a client-side convenience. The ACL is the enforcement.

---

## 5. Review Campaign

**Table:** `x_2182277_access_0_review_campaign`

| Operation | Role | Condition |
|---|---|---|
| `create / read / write / delete` | Per table-creation wizard defaults | None |

Campaigns are container records carrying no entitlement detail. They are created by the scheduled flow running as System. Access is not further restricted.

---

## 6. Roles and Delivery

Roles are assigned to **groups, never directly to users**.

| Group | Role granted |
|---|---|
| Access Requesters | `x_2182277_access_0.user` |
| Access Reviewers | `x_2182277_access_0.reviewer` |
| Access Managers | `x_2182277_access_0.access_manager` |

Direct role grants are avoided deliberately. Group-derived roles appear in `sys_user_has_role` with `inherited = true`, making provenance visible: the grant can be traced to a group-membership decision rather than an untracked one-off assignment.

Removing a user from the group removes the access.

This is the same principle the application enforces on the entitlements it manages, applied to the application's own permissions.

## 7. Verification Method

The row-level read control was verified functionally rather than by inspecting ACL records, using three impersonated sessions against the same list view:

| Session | Records visible | Expected |
|---|---:|---|
| Requester (`.user`, 4 own entitlements) | 4 | Own records only |
| Access Manager (`.access_manager`) | 16 | All records |
| Administrator | 16 | All records |

> **Why functional testing matters:** Inspecting an ACL form shows that a rule exists. It does not show whether that rule is the one deciding the outcome—another rule may grant the same access, or the account under test may bypass ACLs entirely. Only impersonation demonstrates effective access.

Editing ACLs requires `security_admin` elevation. Elevation is session-scoped and must be re-acquired each session.
